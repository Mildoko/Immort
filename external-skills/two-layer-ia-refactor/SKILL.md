# 交互案「跨层副本混乱」的结构性重构

## When to Use

一份交互案（20+ 界面）**脚本审计 PASS、但读起来是乱的**：

- 同一条规则在 2–3 处有不同数字（确认弹窗「2 处 / 3 处」、轻提示「3/4/5/6 种」）
- 层级声明与结构自相矛盾（写「全案不存在二级链路」，但表里就是二级链路）
- 组件规格与用法漂移（规范写 A 尺寸、界面写 B 尺寸）
- 头部 `status` 落后于正文、版本记录乱序

**不适用**：只有一两处笔误、或纯粹的界面细节问题 —— 那种直接改即可。

> **第一条纪律：不要逐条打补丁。** 这些症状的共同病因是「**同一件事写了多遍、各自迭代过**」。逐条修必然留下新的副本。**正确顺序是先收敛结构（IA / 单一真源），再回头改逐界面。**

## 判据：这是 IA 层问题，还是逐界面问题？

问一句：**「把其中一页改好，其他页会自动跟着对吗？」**

- 会 → 逐界面问题，直接改。
- 不会（改了 A 页，B/C 页还是旧口径）→ **IA / 全局约定层问题**，走本流程。

---

## 步骤

### 1. 先诊断，不做修改

把文档按**权威层级**切成四块，逐块找「跨层副本」：

| 层 | 典型位置 | 应扮演的角色 |
| --- | --- | --- |
| **全局约定层** | §2 全局交互约定（G1/G2…） | 返回 / 弹窗 / 空态 / 轻提示 / 手势的**唯一定义处** |
| **跳转表层** | §3.2 按钮级追踪表（J01/J02…） | 每条跳转的**唯一定义处**（起点/触发/终点/落地/返回/传参） |
| **界面清单层** | UI 规范 §14（IA 分层 + S## 清单） | 界面数量与分层的**唯一定义处** |
| **逐界面层** | §4.x 每页三段（概述 / 结构 / 提示词） | **只引用**，不自行发明规则 |

产出：一张「冲突清单」，每条写明**三处口径 + 出处**，并标注性质（规则冲突 / 行为冲突 / 完整性 / 组件漂移 / 布局错误 / 文档卫生）。

> **这份清单要写进文档**（本案落在 04 §5.1「v2.4 重构解决的既有缺陷」）。它是下一轮评审不再翻旧账的依据。

### 2. 找「被压成一层」的那两个层 ★

绝大多数这类混乱的**根因只有一个**：**两个本应独立的界面层被压成了一页**，于是各自的功能入口挤在一起，时间一长谁都要改它、谁都在它上面留副本。

本案：`主场景`（元游戏中枢）与`关卡`（棋盘作业区）被压成一个「绿洲沙盘」页 ⇒ 商城 / 图鉴 / 签到 / 设置 / 复苏 / 在线奖励全挂在棋盘上。

**拆之前先立一句可复述的归属判据**（没有判据，拆完还会再混）：

> 本案判据：**「这件事是不是发生在棋盘上」** —— 是，留关卡；不是，归主场景。

**判据要写进两层定义表**，让后续每个新入口都能自查。

**关卡页/作业页要追求「纯净」**：本案明确「关卡只留体力 + 金币 + 棋盘数据」，宝石与钥匙（局外资源）一律不进。**给每一层写清"不挂什么"，比写清"挂什么"更有约束力。**

### 3. 收敛为单一真源

- 规则 → 只留在**全局约定层**，逐界面**引用编号**（`（G6）` / `（J53）`），不重述。
- 跳转 → 只留在**J 表**，逐界面写 `（J53）`。
- 数量/分层 → 只留在**界面清单层**。
- 逐界面章节**删掉**一切「本页规则也适用于全案」的措辞。

### 4. 编号纪律（**别重排，改定义**）

- **号段沿用不改**：改 S03 的**定义与形态**，不重排 S01–S20（重排会打断全案交叉引用）。
- 新增界面**排末尾**（S21 / S22…）。
- 被废的条目**显式留痕**，不要留纯空号：`| ~~J48~~ | ~~旧起点~~ | **[日期 废]** 原因 + 替代者 | — | — |`
- 作废行**带 `~~` 前缀**（这样审计正则跳过它，见「坑」第 3 条）。

### 5. 逐界面改写

按**依赖顺序**改，一次改完再跑审计：

1. 全局约定层（层级声明 / 数量口径 / 行为口径）
2. 界面清单层 + 跳转表 + 导航图 + 可达性表
3. 受影响最重的界面（本案：被拆的那一页 + 新增页）**整节重写**
4. 轻触界面的出口/入口/引用（半天以内的改动批量做）
5. 收口：审计结果表、待决策表、版本记录、`status`
6. **跨文档连带**：IA 一改，别的文件会跟着错（本案：美术资产规范里的取景规则、玩法策划案里的入口引用）—— 全库 grep 旧术语

### 6. 重跑审计并清零

```
python3 tools/audit_interaction_docs.py .
python3 tools/audit_numeric.py .
```

## 大改动的前置动作：先落「提案稿」

**不要直接改 1500 行的正文。** 先新建一份**提案稿**（本案 `08_信息架构重构.md`），只写：两层定义 / 归属边界 / 界面清单重排 / 跳转表变更 / 待决策。**拍板后**再一次性落进正文，并在提案稿里保留决策记录 + 落地动作清单。

好处：① 结构讨论与逐界面写作解耦；② 拍板过程有据可查；③ 正文只被改一次。

## 两道验收

| # | 验收 | 做法 |
| --- | --- | --- |
| 1 | **脚本** | 两脚本 exit 0；重点看「界面覆盖 / 孤儿 / 死链 / 命名 / 取值闭环 / 清单一致性」 |
| 2 | **人工（脚本查不到）** | ① 把冲突清单逐条回查是否已消；② **「作业页洁净度」**：逐项核该页**没有**任何不该出现的入口（本案列为审计第 8 项，明确注明**不可脚本化**，因为「某入口算不算运营」是语义判断） |

> **纪律：凡脚本查不到的，就在文档里写明「此项由人核，不进脚本」。** 否则下一轮会误以为脚本绿灯等于全绿 —— 本流程整个起因就是这个误解。

---

## Pitfalls

1. **把「脚本 PASS」当成「设计正确」** ★ —— 这是本流程存在的唯一理由。脚本查的是机械一致性（有没有定义 / 有没有入口 / 有没有死链 / 名字对不对），**查不出「同一条规则在几处有不同副本」**。诊断时别跑一遍脚本看到绿灯就收工。
2. **逐条打补丁而不收敛结构** —— 补丁会制造新副本。必须先收敛真源。
3. **审计脚本的正则陷阱：加粗 ID 单元格会让条目整体不被解析** ★ —— 常见脚本按 `^\|\s*(J\d+)\s*\|` 抓行；写成 `| **J53** |` 时 `**` 挡住了匹配 ⇒ **该条静默消失**，连带把它的目标界面误报为「孤儿」。**同一坑对界面清单同样成立**（`| **S21** |` 不计入清单 ⇒ 报「写了但清单里没有」）。
   - **纪律：ID 单元格一律不加粗**；想强调就加粗**名称**列。
4. **中文字档里的引号** —— 改中文正文时手误写半角 `"` 会替换掉中文引号，造成全篇混用；改完 grep 一遍。**patch 的 escape-drift 报错**：old_string 里含 `\"` 时匹配会失败 —— 改用**不含引号的短锚点**分两次替换。
5. **提案稿直接当正文改** —— 长文档一次改错代价高；先提案、拍板、再落地。
6. **只改被点名的那份文档** —— IA 是跨文档的。本案连带：美术资产规范的取景规则（横版扁条 → 竖屏通铺）、玩法策划案里的界面引用、评审报告里的旧建议。**每次 IA 改动后全库 grep 旧术语**（旧界面名 / 旧尺寸 / 旧编号）。
7. **拆层之后忘了资产/布局的连锁** —— 本案：关卡页去掉侧栏 ⇒ 内容宽恢复 960 ⇒ **物品格上限从 126 变成 136**（旧值本是「侧栏 + 不滚动」下的被迫上限）。**「某个约束解除」要立刻回查它当初压出来的那几个数**，并写进规范作显式新上限。
8. **新增界面后忘了让脚本认识它** —— 新增项必须同时进：界面清单层、跳转表（**至少一条入边**，否则报孤儿）、以及它自己的章节标题（命名要逐字一致）。
9. **一次推太多条** —— 逐条改、每条改完确认再下一条；末尾留「待决策项」批量拍板。

## 变体：当两个 L0 都需要「首页」资格时

如果拆出来的两层都够格当落地页，**别用底部 Tab 硬塞**（本案沿用「单场景沉浸式、不做 Tab」的惯例）。做法：**定一个为落地页，另一层由它上面的唯一主 CTA 进入，并在被进入侧的顶栏放返回位**。同时把「层间往返」写进导航纪律，并把「除这两层外，其余一律一级纵深」写成显式条款。
