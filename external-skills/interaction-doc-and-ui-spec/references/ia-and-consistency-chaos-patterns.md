# 「审计 PASS、设计仍乱」的排查手册

## 现象

交互案审计脚本（`audit_interaction_docs.py`）退出码 0，但方案整体混乱。
原因：脚本只查**机械一致性**（有无定义 / 有无入口 / 有无死链 / 命名 / HEX 闭环），
**查不出规则本身的冲突** —— 这正是 SKILL.md §5.2 写明的局限。
所以「脚本通过」永远不能当作「设计正确」的证明。用户说「完全混乱」时，先跑下面这套排查，再动手改。

## 四类脚本看不见的乱（实测于「绿洲」交互案）

### 1. 同一条规则在 2–3 处口径不同（最根本的乱）

- 确认弹窗数量：§2.1 写「仅两处」/ §2.5 写「全案唯一」/ §4.20 写「共 3 处」；
  且 §2.1 里那个「退出支付流程」二次确认在跳转表里**根本不存在**。
- 短气泡内容：标题写「五种」→ 实际列 6 条字符串 → 旧留痕写「三种」→ 审计按「6 条」判 PASS。
  **3 / 4 / 5 / 6 四个数字并存。**
- 排查法：把同一概念的**关键词拿去 grep**，把每处命中的**数量口径并列比对**，不靠肉眼记。

### 2. 规则自称 vs 结构实际矛盾

- §2.1 声明「全案不存在二级链路」，但 S07→S19、S15→S16 就是二级链路，
  且 S02 / S17 / S19 还标着 L2。
- 排查法：把「纪律 / 总则」段落里的**绝对词**（唯一 / 仅 / 不存在 / 一律 / 全部 / 不得）
  逐条拿去 grep 找反例。绝对词越多，藏着假声明的地方越多。

### 3. 跳转表自身有洞

- **跳号**：编号从 J18 直接跳到 J20（缺 J19），而正文又引用「J05–J21 共 19 条」。
- **单向缺失**：某界面出口漏了一条（S05 出口漏 `Odds`→S06），
  可导航图 / 映射表 / 目标页入口三处都认它。
- 排查法：脚本抓不到「漏写」。必须**逐界面出口 × 映射表 × 导航图**三处对表，找单向出现。

### 4. 组件规格（规范）与用法（交互案）不同步

- 签到格：规范「7 列 × 2 行 / 120×120」 vs 用法「7 格一行 / 110×110」。
- 装饰位：规范「场景内 6 个固定锚点」 vs 用法「6 格 × 1 列网格列表」—— **两种模型**。
- 「一屏全见」类承诺要**算一遍**：6×152 + 5×24 = 1032，再加页头与底部行 ⇒ 超一屏，承诺失效。
- 排查法：把规范里每个组件的尺寸，拿去 grep 交互案里同名组件的用法，逐一比数。

## 顺带的文档卫生

- **状态行 / 版本记录失真**：状态行仍写 `v2.1` 而正文已到 v2.6 内容；
  版本表乱序（v2.3 排在 v2.2 上面、v2.6 排在 v2.5 上面）。
  状态行要么删掉，要么每次同步 —— 留着错的就是第三个真相。

## 报「乱」时的分层口径（先定层，再动手）

1. **架构层** —— 两层（主场景 / 关卡）被压成一层 ← **最优先**，一改则下面几层的很多矛盾自动消失
2. **规则层** —— 同一真相被复制到 2–3 处且各自漂移
3. **表层** —— 跳转表跳号 / 单向缺失 / 返回路径未进例外清单
4. **组件层** —— 规范与用法不同步、布局承诺算不平

先给用户这份**分层诊断**（可核对的具体冲突 + 出处编号），再问「先动哪一层」——
不要一上手就逐界面修补，那是在错误的层上做功。

## 改完之后：在文档里留一张「本次重构解决的既有缺陷」表 ★

修完**必须**回到交互案，新增一节把这批缺陷**逐条列表化**（缺陷 / 性质 / 处置），并写明一句总结：

> **为什么非写不可**：这些缺陷的共性是「**脚本绿灯、肉眼也未必看得出**」。不写下来，下一轮评审会：
> ① 以为文档本来就对，拿同一句假声明再卡一次；
> ② 或反过来重新引入（例如又把「确认弹窗 2 处」抄回去）。
> 这张表是**给未来的自己**看的，和「已废弃命名方案（勿再使用）」是同一类留痕。

**表的每一行要带出处编号**（§2.1 / §4.20 / 03 §九…），否则读者无法核对。**不要只写「已统一」** —— 要写「原 A 处写 X、B 处写 Y、C 处写 Z → 现统一为 W」。

## 顺带的两条交付纪律

- **编号沿用、新增排末尾**：重构时不要在既有清单里重排编号。改的是「某个编号的**定义**」，新增的排到最后（如 S21 / S22）。重排编号会让全案交叉引用返工，收益为零。
- **头部与版本记录同批修**：状态行 / 版本表在最上面，最容易在长任务里被漏掉，漏了就是「第三个真相」。
