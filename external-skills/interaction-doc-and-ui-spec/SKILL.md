# 交互案 / 通用交互案 / 美术规范 撰写方法论

## When to Use
- 将产品拆分为多个系统后，为每个系统产出「交互案」
- 需要补齐多系统之间的界面跳转衔接（「通用交互案」）
- 需要一套指导所有 UI 生成的美术规范（色彩/字体/画布）

## 写作标准（强制，先做这一步）
写之前先 `skill_view(name='ste-writing-standard')`，并按它加载 `asd-ste100`。交互案与 UI 规范按 **STE100 的 80–100% 严格度**写：**界面文案、按钮、系统提示、失败兜底 = 100%**（这些字会进游戏，歧义直接变成 bug），**设计理由与取舍说明 ≈80%**；英文文案必跑 `ste-lint.py`；中文只借结构规则。**剧情台词与营销文案不适用** —— 它们走项目自己的叙事约束。

配套关系：`game-system-doc-template` 是**策划案**模板（讲规则/数值/配置）；本 skill 是它的**交互侧姊妹篇**（讲用户如何操作）。AI Agent/工具类产品的策划案还要叠加 `agent-product-design-framework` 的四层架构，但交互案结构不变。

## 一、交互案（Interaction Doc，每个系统一份）

与策划案分离，聚焦「用户如何操作这个系统」。标准六段结构：

1. **用户旅程（核心路径）** — 单行流程图：`[入口] → [状态] → [行动分支]`
2. **页面清单与状态机** — 每个页面列出各状态（默认态/空态/加载态/异常态/冷启动态），表格呈现
3. **操作矩阵** — 表格列：`操作 | 前置条件 | 状态变化 | 反馈 | 埋点 | 可撤销`
4. **关键界面布局** — 自上而下的区域说明
5. **异常/空态/兜底** — 表格：`场景 | 交互表现`；空态必须带「引导文案 + 动作按钮」，禁止空白死路
6. **不含验收** — 验收要点属**测试/验收阶段**，从交互案剥离，统一收进独立的《验收文档》（用户明确：验收不是设计阶段的事）

## 一.5 分批交付纪律（决策未定不画界面）

交互案往往 20+ 个界面，一次性交付既超长又高风险，而且**有些界面的布局被尚未拍板的决策直接决定**。按「是否依赖未决策项」把一份交互案切成两半：

- **先交不依赖任何待决策的那半**：全局交互约定（返回 / 弹窗 / 加载 / 空态 / 异常 / 轻提示 / 跨天 / 手势 / 数值变化）+ 界面清单 + **按钮级跳转映射表** + Mermaid 导航地图 + 可达性检查。它钉死的是**所有界面的公共前提**，逐界面写作才不会出现「同一个动作在不同页表现不同」。
- **被待决策阻塞的界面一律先不画**。反例：某主界面同时被「功能入口形态（侧边栏 vs 场景建筑）」与「棋盘格尺寸（决定是否溢出需滚动）」两项卡住 —— 这两项直接决定主界面布局，规则没定就画 = 白做。这与「先定规范，再做界面」是同一条纪律的延伸：**不只规范要先定，决定布局的参数也要先定**。
- 交付时**把阻塞项逐条点名**（哪一项卡住哪一批），并说明「给我 A/B/C 我就能出下一批」——比笼统问「还有问题吗」有效得多。这是「不应在无进展时反复空问」的正解：不是不许问，而是**把问题变成有明确出口的选择题**。

配套两条编号纪律：**全局交互约定编号（G1/G2…）**，逐界面引用编号、不重复展开；**跳转映射表编号（J01/J02…）**，作为所有界面提示词里「跳转 XX」的权威定义。

映射表里最容易被漏的一类是**「资源不足之后去哪」**（如金币不足 → 回主界面并定位到产出区高亮、传 `intent=earn_coin`；高级货币不足 → 商城并传 `focus=<资源>`）。漏了它，界面提示词里那句「跳转商城」就没有落地页与传参，系统沦为孤岛。

## 二、通用交互案（全局/跨系统一份）

拆分多系统后，各系统交互案常是「单向箭头」——只写「跳转 XX」却缺落地页/返回路径/传参，系统沦为孤岛。通用交互案补齐这些「衔接件」：

1. **全局导航框架** — 底部 Tab 结构 + 各系统归属 + 切换规则；二级浮层（地图/拍照/战报等）不入 Tab
2. **首页聚合** — 意图输入框 + 速览卡 + 各系统快捷入口
3. **跨系统跳转映射表（核心）** — 编号 J1–Jn，每行：`起点 | 触发 | 终点 | 落地页 | 返回路径 | 传参`；作为所有分系统交互案中「跳转 XX」的权威定义
4. **扫码落地页（拉新第一屏）** — 区分新用户（引导注册）/老用户（直达功能）
5. **推送/通知落地规则** — 各类型推送点击后的落地页
6. **关键「去向」决策** — 如发布后去向、急救包落地、空态引导，明确「这个动作之后用户去哪」
7. **统一交互约定** — 深度链接 Scheme、返回手势、空态/加载/异常的统一表现

## 三、美术规范（全局一份，指导所有 UI 生成）

从产品调性推导风格与语言，全部给**可执行参数**（非形容词）：

- **画布基准** — 分辨率 + 栅格 + 页边距 + 安全区 + 适配倍率
- **调性/风格定位** — 由产品调性关键词推导「轻拟物/扁平」等风格定位
- **色彩系统** — 品牌主色/辅助色/功能色/中性色，全给 HEX；含语义分级色（如评分分级色）
- **字体/排版（必须完整，不能只给色彩/间距）** — 8 级文字层级（Display/H1/H2/H3/Body-L/Body/Caption/Footnote），每级给 **字号 + 字重 + 行高 + 颜色 + 使用场景**；另有文字颜色体系（主/次/弱/反白/品牌强调/状态色）与排版规则（行高、字间距、段落间距、对齐、截断、数据用等宽数字）。用户明确纠正过：只写色彩与间距「过于简单」，各级文字都要在**基准分辨率下**给出明确约束
- **图标/圆角间距/质感动效** — 给具体描边 px、圆角 px、时长 ms、缓动
- **吉祥物规范** — 多表情状态对应各触发场景（推送梯度、加载、结算）
- **特殊视觉双轨** — 如战报海报「爆护热血风 / 自嘲像素风」两种风格
- **AI 产线样张闸门（凡素材走 AI 生成就必须写进规范）** — 规范里要写死：**批量生成前必须先出 2–3 张样张经确认，否则不许批量生产**。样张挑「最可能崩的地方」，不是挑最好看的：① **同升级链多阶并排**（验视角 / 线宽 / 受光 / 材质是否真的统一 —— 品类最容易崩处）② 场景演化图 ③ 角色形象（兼验市场文化合规）。出图参数：**单张独立生成**（拼图会互相污染风格）、**纯色底便于取色**、每张出 4 张择 1。样张确认后必须把实测到的色值 / 线宽 / 材质语言**回填规范**，后续界面才有统一基准。完整作法（含"对比轴必须匹配验证目标"）见 `meta-game-build-families` §七–§八

**规范里最容易漏、但下游一定会出问题的七项**（实测逐项被下游引用时才暴露）：

| 缺什么 | 后果 | 补法 |
| --- | --- | --- |
| **语义色的形状冗余** | 只靠颜色区分等级时，色觉障碍用户完全分不开（如黄绿 vs 橙） | 每个语义档除颜色外**各配一个形状图标**（双勾/单勾/横线/叉）。这是**无障碍要求不是装饰**，且要在规范里写死"任何用到该语义的地方都不得只用颜色" |
| **图标语义表** | 同一个语义在不同界面画成不同形状，用户以为是两个功能 | 一张「语义 → 固定形状 → 用在哪些界面」的总表，全案共用 |
| **动效库 + 两条纪律** | 各处自造动效，节奏全乱 | ① **不用转圈 spinner** —— 加载与等待用**角色表情**（吉祥物打瞌睡/出汗）或元素脉动；转圈让人以为"系统卡了"，角色表情让人以为"它很努力" ② **摆动 ≠ 抖动** —— 拦截/未达标用阻尼摆动（如 ±6px×3 次、`ease-in-out`），抖动像"报错"、摆动像"没听清，再说一次" |
| **状态与反馈规范（"状态的视觉语言"表）** | 实现时习惯性加回一堆弹窗，与零文本/极简文案规范打架 | 写一张对照表：想表达「可以点」用什么、「不能点」用什么、「刚才是错的」用什么、「在等」用什么、「成功了」用什么。并显式写明「**不弹 toast、不弹错误提示，所有状态用界面状态本身表达**」 |
| **CSS 变量速查** | 前端各自硬编码色值，规范形同虚设 | 把色值/字号/圆角/间距/动效时长整理成一段可直接复制的 `:root {...}`，标注"前端可直接落地" |
| **热区与最小尺寸** | 触屏上按钮点不中 | 显式写「最小热区 ≥44×44，允许视觉尺寸小于热区」 |
| **允许出现文字的例外清单** | 零文本/极简文案原则被执行成"什么都看不见"，或反过来到处冒出说明文字 | 列一张例外表：哪些位置**仍必须有文字**（练习内容本身、游戏数值、发音音素标签、浏览器权限引导），其余一律图形化 |

**规范独立成文后要留"唯一性声明"**：如果规范起初是内嵌在某个交互案的 `§0`（见下文的权宜做法），
抽成独立文件后必须回到那份交互案，把原节**标记为「已迁移 / 历史留痕、不再维护」**，
并写明「以独立规范为准，不一致以规范为准并回改本文」。否则同一套视觉会出现两个真相。

## 四、界面提示词（每个界面一份，含入口/出口）

交互案的落地是「界面提示词」——每个界面一份，用于 AI 生成 UI 或给设计师。标准三段：

1. **界面概述** — 类型（Tab主页/二级页/组件/弹窗）、目标、**入口（上游）**、**出口（下游）**
2. **完整结构（自上而下）** — ① 导航栏 ② 内容区 ③ 底部操作，逐模块拆元素/样式/文案
3. **生成提示词** — 中文 + 英文两版，可整段复制（画布+结构+元素+样式+文案）

**铁律：做界面时就定义入口和出口**（不是做完再补导航）。每个界面必须写清上游（从哪个界面的哪个按钮进）和下游（每个按钮点到哪去）。事后补导航 = 界面成孤岛（本会话就是先做 49 个界面、后补导航，代价很大）。

### 写「生成提示词」的六条纪律（不做就会得到一批风格漂移的图）

把提示词模板固化进规范，每个界面按同一骨架写，缺一不可：
`画布 / 结构（自上而下逐层给高度）/ 布局（边距·间距·对齐·视觉焦点）/ 元素（逐项给尺寸+圆角+描边+色值）/ 样式（背景·卡片·阴影）/ 文案（写"零文本"或列出例外文字）/ 状态差异 / 生成提示词（中文）/ 生成提示词（English）`

1. **色值写死在提示词里** —— 生成工具读不懂变量名，必须给十六进制。
2. **界面是零文本时必须显式写「无文字 / no text anywhere」** —— 否则生成的图会自己塞一堆英文占位文字。
3. **必须写「无 3D、无写实光影」** —— 否则风格会往写实漂。
4. **尺寸与圆角给具体数字**，不给「较大」「圆润」这类形容词。
5. **多状态控件要并列展示所有状态**（如按钮的就绪/激活/加载/不可用四态并排出一张图），美术才有对照。
6. **中英双版内容必须一致**，不得一版详细一版简化。

## 四.5 布局算式先行（写界面提示词的第一步）

**写任何界面提示词之前，先把该界面的纵向与横向布局算式写出来**（每块的高度/宽度 + 间距 + 安全区，求和后与画布尺寸对比），并**把算式写进界面文档**（一个代码块，逐行列「段高 + 间距 + 安全区 = 画布高」，末尾标 ✓ 与余量）。

**算式的真正价值：它会逼出规格冲突。** 实测设计一个主界面时，算式当场撞出三处不自洽：

| 撞出的问题 | 算式 | 修正 |
| --- | --- | --- |
| 核心操作区放不下 | 新增 132 px 侧边功能栏后横向只剩 948 px，而 7 列 × 130 px = 910 px + 60 px 页边距 → 爆 | 格子 **130 → 126 px**（7 × 126 = 882） |
| 组件宽度与容器对不上 | 3 槽订单卡 + 2 × 18 px 间距须等于容器宽 882，原规格是按 912 算的 | 卡宽 **288 → 282 px** |
| 纵向刚好溢出 | 各段求和正好 1920，零余量 | 重排各段，留 20 px 余量 |

**三条纪律**：

1. **算式写在文档里**（不只留在脑内）—— 日后任何一段改动都能立即重算，不会靠记忆。
2. **算式逼出的规格修正必须回补进 UI 规范并升版本**，规范里写明修正理由（这就是「新元素回补规范」在数值维度的同一条纪律）。
3. 若修正产生**「上限/下限」型连带结论**（如「在侧边栏 + 不滚动两个前提下，**126 px 是格子尺寸上限**」），**必须写成规范里的显式约束** —— 否则后续界面会把它重新当作可调项，反复推翻。这是把一次推导转成永久约束的动作，价值最高。

> **前置提醒**：像「功能入口用侧边栏还是场景建筑」「核心操作区尺寸」这类决策会**直接改写布局**，属于**必须先拍板再做界面**的一项（见 §一.5）。别画完才发现要重排。

## 五、界面审计（脚本化，收尾必做）

全部界面做完后跑机械审计，别靠肉眼：
1. **导航章节**：每个界面都有「入口/出口」段
2. **孤儿界面**：每个界面被某处引用（Tab 主页、从推送/运营端进入的除外）
3. **死链**：出口提到的界面名真实存在
4. **命名一致性**：界面名与引用名**逐字一致**（「动态feed」vs「动态 feed」一个空格就误报孤儿）
5. **缺失界面**：被引用但文件不存在 → 补建
6. **规范收口校验**：把**所有界面提示词里出现的取值**（颜色 HEX / 尺寸 / 圆角）收集起来，断言它们**都在《UI设计规范》里定义过**。
   凡文档声称"提示词引用规范、规范没覆盖的补回规范（闭环）"，就必须有一条脚本能跑出这句话。
7. **映射/对照表覆盖度校验**：规范里若有全集-子集型表格（如"厂商 n 个取值 → 归并为 m 个档位"），
   拿**全集**与**表中集合**求差，报漏 / 多 / 一个键映射到多个值。凡写了"全部覆盖"，同样要能跑出来。
8. **废弃取值残留扫描（反向收口）** —— 与第 6 条**方向相反**：某色值 / 尺寸 / 术语被**作废或整体换代**后（色板换代、命名改名、单位统一），全案 grep 旧值，**除「已废弃 / 作废 / 替代原 X」这类说明外不应有任何残留**。
   实测：夜景底色换了新色板后，一条 grep 又抓出 **5 处残留**（角色立绘配色、主界面场景区天空、抽奖页背景渐变…），全部要同步 —— 不扫就会留下两套底色并存，下游各拿一版。
   判据：**「单向替换 + 有条件排除」的 grep 必须真的跑一遍**，不能凭记忆认为"只改过那一处"。做法：`grep -rn '<旧值>' <文档目录> | grep -v '作废\|替代原'`，期望无输出。

改完重跑，直到「孤儿=0、缺导航=0、**未定义取值=0、映射漏项=0、废弃取值残留=0（废弃说明除外）**」。

- **扩展脚本（推荐主力）**：`scripts/audit_interaction_docs.py` —— 六项一次跑完（界面覆盖 / 入口·出口完整性 / 跳转死链 / 孤儿 / **取值闭环** / **命名一致性**），退出码 0 = 通过，可直接进 CI 或交付前最后一步。用法：`python3 scripts/audit_interaction_docs.py <文档目录> [规范文件名] [交互案文件名]`（兼容「一份规范 + 一份交互案」的文档集；界面切分正则可通过 `SCREEN_RE` 常量调整）。
- 基础版 `scripts/audit_screens.py` 仍适用「每个界面一个 md 文件」的目录结构。

### 5.1 严重级必须区分：**「用了但没定义」是硬错误，「定义了但没用」只是冗余** ★

两类问题的处置强度必须不同，否则审计会撒谎、或被迫为了让检查通过而删掉有用的东西：

| 检查 | 性质 | 处置 |
| --- | --- | --- |
| 提示词里用了某个 HEX / 取值，**规范里没有定义** | **硬错误** | **必须 FAIL** —— 提示词写死的值没有规范来源，下游无人维护它 |
| 规范里定义了某个值，**全案没有任何地方用** | **冗余，不是错误** | **只作提示**，不计失败。可能仍被规范自身的概念性描述使用（如「1 帧白色高光」） |

> 实测教训：第一版脚本把「定义但未使用」也算 FAIL 了 —— 那等于**让审计工具替我们决定删掉调色板里的纯白**。修正后才对：硬错误一票否决，冗余只提示。**凡把非错误当失败，工具就会被绕过。**

### 5.2 已知局限：脚本查「机械一致性」，人查「设计正确性」★

把局限**写进文档**，否则下一轮会拿它当万灵药，或者反过来因为一次误报而整个弃用：

| 局限 | 说明与对策 |
| --- | --- |
| **「使用」是按正则扫全文，不区分「设计使用」与「行文提及」** | 文档里讨论某个色值的正文也会被算作「已使用」⇒ **「未使用」提示项仅供参考，不能当洁净度指标**。反向的「用了没定义」不受影响（提及同样需要定义） |
| **查不出逻辑错误** | 只能查一致性与完整性（有无定义 / 有无入口 / 有无死链）。**数值是否对齐、交互是否合理、提示词能否出图**，必须人看 |
| **查不出「没进清单的界面」** | 若某界面既没进规范清单、也没写进交互案，就不在扫描范围内 ⇒ **采清单为准，清单本身错了脚本发现不了** |
| **只校验 HEX** | 字号 / 间距 / 圆角 / 时长目前靠规范约束，尚未纳入脚本。一旦下游出现「提示词里的字号规范里没有」，就把收口检查**扩展成通用取值扫描**（`\d+px` / `\d+ms` 等） |
| **查不出「跨层副本」（最大盲区）** | 脚本只比**被显式指定的两处**是否一致（如检查 7 比 §2.6 ↔ §4.20③），**不会主动去找还有哪些规则被写了多遍**，也不判断「这条规则本该只定义在一处」。实测：v2.3 及以前脚本长期 PASS，文档其实是乱的（确认弹窗 2处/3处、短气泡 3/4/5/6、层级假声明）⇒ **脚本绿灯 ≠ 设计正确**。对策：由人先按「全局约定 / 跳转表 / 界面清单 / 逐界面」四层列候选再逐条比。**诊断清单见 `references/ia-and-consistency-chaos-patterns.md`，动手流程见 skill `two-layer-ia-refactor`** |

> 一句话：**凡是能用脚本断言的事，就不要再靠肉眼；但脚本通过 ≠ 设计正确。**

### 5.3 写审计脚本本身的三个坑（实测各踩一次）

1. **表格列索引要按表头数，不要凭印象** —— 跳转映射表的列是 `J号 | 起点 | 触发 | 终点 | 落地页 | 返回路径 | 传参`，脚本按 `split("|")` 后**终点是 `cols[2]`**。第一版取成 `cols[1]`（触发列），结果 45 条跳转全部报「终点无法解析」，并连带把 17 个界面误判为孤儿。⇒ 解析前先数一遍表头。
2. **命名比对要先剥掉括注，只比主名** —— 规范清单写「神灯祈愿（开箱）」、交互案章节写「神灯祈愿（L1 · 变现入口）」，若把括号内一并纳入比较，会产生纯误报。做法：`re.split(r"[（(]", s)[0]` 取括号前主名，再逐字比。⇒ **凡是「A 处与 B 处名字要对上」的校验，先定义清楚「名字」包不包含括注。**
3. **★ 编号列绝对不能加粗（最阴的一个坑）** —— 两个核心正则都是 `^\|\s*(J\d+)\s*\|` 与 `\|\s*(S\d{2})\s*\|`，**要求编号紧跟 `|`**。一旦把新增条目写成 `| **J53** | …`、或把界面清单行写成 `| **S21** | …`，正则就匹配不到 ⇒ **该行被静默跳过**。症状是「03 清单声明 20 / 04 实际交付 22」但两个方向都报「✓ 无差异」，以及**新增的界面被报成孤儿 + 死链**（因为它既不在 `listed` 也不在 `targets`）。**它不报错，只是少算** —— 最容易被当成方案有问题而回头改文档。⇒ 新增条目的**编号一律不加粗**，加粗只用在名称/说明列；发现计数对不上先去查这个。
4. **作废的跳转条目用 `~~` 显式留痕，不要直接删** —— 被替代的 J 号写成 `| ~~J10~~ | ~~起点~~ | **[日期 废]** 原「…」—— 改由 **J55** 承担 |`：`~~` 让正则跳过它（不进死链检查、不进目标集），同时**保留了「这个号被用过、为什么废」的记录**，也避免出现无法解释的裸空号（实测旧版就有 J18 直接跳 J20 的空号，而正文还引用「J05–J21 共 19 条」）。⇒ 与命名一节同一条纪律：**淘汰要有黑名单，不要留白。** 注意：保留 `~~Jxx~~` 行会让「J 表条目总数」比实际有效跳转多几条，写审计结论时要一并说明。

### 5.4 重审触发时机（写进文档，让它成为交付流程的一部分）

改以下任一处后**必须重跑**：新增 / 删除 / 重命名界面 → 检查 1/2/4/6；改动跳转表或任何界面的出口 → 检查 3/4；**在提示词里写下任何新的 HEX** → 检查 5（**最容易漏的一项**）；改动规范的清单或交互案的章节标题 → 检查 1/6。

> 收口检查的第三类真实缺陷实例（与上面的 `#FFFFFF`、`#F0EBE3` 同类）：某抽奖页提示词里写了「保底前辉光转为更亮的 `#FFD86B`」，**规范未定义** —— 它看着与旁边的金色 `#C9A227` 很像，扫一眼只会觉得\"这是个金色系的值，没问题\"，靠肉眼绝无可能发现。**同一失败模式反复出现，正说明它必须脚本化。**

> **实测价值**：这两条收口校验各自抓到了肉眼看不出的真实缺陷 ——
> ① 三份交互案里共 2 个色值（`#FFFFFF`、`#F0EBE3`）在提示词里用了但规范没定义，"闭环"当场破功；
> ② 一张 48 项 → 12 档的映射表手写漏了 2 项，且漏掉的正好落在已存在的档位旁边，扫表根本发现不了。
> **这两类错靠肉眼审是审不出来的**，必须脚本化。

## 六、信息架构分层

做完界面必做分层，否则入口页与详情页会被做成平级（本会话的典型错误：用户中心 vs 成长中心）：
- **L0 Tab 主页面**：底部导航直达（首页/消息/我的/发布）
- **L1 下级页**：Tab 内点入口进入（成长中心、搭子、斑币…）——**入口页（如「我的」）是聚合页，详情页是它的下级，不要平级**
- **L2 流程页**：业务流程串联（详情→报名→支付→凭证）
- **组件/弹窗**：非独立页（洞察卡、评价摘要）

**旁证**：不要为「某个能力/看板/体系」单独建文档——它该融入所属模块（本会话用户纠正：数据看板应融进「主理人」「用户」两个模块，而非独立的《数据看板体系》）。

### 6.1 关卡型 / 二合游戏的「主场景 + 关卡」两层 ★

对**有「局外经营（主场景）」+「局内作业（关卡）」双形态**的产品（二合 merge-2、消除、塔防…），信息架构的第一条纪律是 **两层分开、职责不混**：

| 层 | 职责 | 挂什么 | **不挂什么** |
| --- | --- | --- | --- |
| **主场景**（家 / 中枢） | 元游戏推进 + **全部入口** | 场景主视觉、进度推进（原地点建筑，不必另开清单页）、资源顶栏、**商城 / 图鉴 / 签到 / 设置 / 活动 / 礼包 / 装饰** | 局内操作（棋盘等） |
| **关卡界面**（局内作业区） | **只做核心玩法** | **棋盘 + 委托 + 关卡内数据**（体力 / 占用 / 冷却） | 商城 / 活动 / 图鉴 / 设置 / 功能入口栏 —— **一律不挂** |

- **为什么**：把「关卡」写纯，局内才不被打断；把入口全收在主场景，才不会出现「同一功能在三个页都能进、三条返回路径互不一致」。本会话实测的乱源就是**把两层压成了一层**（一个主界面同时承载资源 / 复苏进度 / 棋盘 / 委托 / 5 个功能入口 / 在线奖励 chip），连带出 19 条出口、返回路径分叉、组件规格与用法对不上、布局算不平。
- **参照系**：Gossip Harbor（Microfun）—— 顶部条承载委托与活动进度、局内出现元游戏入口图标，关键是**每一层只有一个职责、入口不撒两处**。（注意：它把棋盘当首页是它的选择，不是二合的定律。）
- **必须先拍的一项**：**「落地页是哪一层」** —— 不要默认「二合游戏棋盘即首页」。本会话（绿洲）取「主场景 = 落地页、关卡由主场景进入」。
- **连带必改**：任何「资源不足 → 回 XX 页定位」的跳转要跟着搬家后的归属改（委托 / 订单在关卡层 ⇒ 金币不足应去**关卡层**，不是回主场景）。
- **层级声明要诚实**：不要写「全案不存在二级链路」这种绝对句 —— 有主场景↔关卡就有两层纵深。改写为「**两层纵深（主场景 ↔ 关卡），其余一步回主场景**」。
- **场景侧的对偶纪律**：主场景一旦成为落地页，场景就从「一条信息带」升级为**通铺整屏的主角**，且必须把「待建位」预画成**坑位**当经营目标 —— 坑位数 = **族位置数，不是项目条目数**（同族升级 = 原位置换图）。见 `references/scene-as-management-goals.md`。

## 六.5 界面文档里的两条「可执行性」纪律

### 待决策项必须自解释

分批交付时抛出的**每个待决策项都要自带术语定义**。反例：某条待决策写「确认 Tier8（128 BU）不进订单池」—— 用户直接反问「**Tier8 是什么**」，说明这条默认了读者知道链/阶体系，等于没问。

- 凡待决策里出现**内部术语 / 缩写 / 档位名 / 代号**，要么括号内一句话定义，要么同条附一张**最小换算表**（如「1 个 TierN = 2^(N−1) 个 T1」）。补上换算表后用户当轮就拍板了。
- 判据：**读者只看这一条就能决策，不必回头翻正文**。
- 同理，**给出"量化影响"比给出"风险"有效**：把「放开会加速内容消耗」写成「日产出 1,609 → 3,207（翻倍），完成日 D19 → D13」，用户一眼就能拍。

### 界面里受法律 / 平台约束的内容要写死禁止项

界面文档是**唯一能让下游（美术 / 前端 / 外包）看见合规要求的地方**，所以必须落到具体界面的具体元素上：

| 约束 | 写法 |
| --- | --- |
| **注册商标** | 在界面文档里**点名禁止**（如抽奖页标题用自造名 `Lamp of Wishes`，并写明「刻意不用 Aladdin —— 那是迪士尼注册商标」） |
| **地区禁项视觉** | 写进生成提示词的禁止清单（如中东区抽奖页写「不得出现筹码 / 骰子 / 扑克 / 轮盘」） |
| **概率公示** | 单独成页（L1 全屏、**纯只读、不得放任何消费入口**），并写死「与数值源文档不一致视为**线上事故**」 |
| **文案口径** | 合规关键句直接写进页脚规格（如 `Rates are fixed and unaffected by spending.` —— 它否认"充钱变欧"，是过审要点） |
| **角色形象** | 立绘类界面的提示词里写死「端庄 / 不透明 / 不贴身 / 无宗教符号与经文纹样 / 不夸张比例 / 不性感化」，并注明**须经本地顾问过审才算通过** |

> **原则**：合规不是附在文档末尾的一节，而是**落到具体界面的具体元素上**。只写在规范里的合规要求，下游看不见。
> 命名的筛查清单（品牌与 IP 冲突 / **宗教专有名词** / 酒烟草赌博联想）与中东市场红线见 `mena-market-naming-and-compliance`。

## 七、AI 生成资产的验收：必须在「最终显示尺寸」下判断 ★

**核心纪律**：生成的图**不能凭原图观感拍板**。AI 出图天生是**概念图级密度**，缩到游戏/界面实际显示尺寸后细节全糊 —— 而这类资产常出现在**常驻界面**（玩家每天看若干次），糊且乱会与相邻的清晰元素（表格、列表项、小图标）抢注意力。

**两道必做检查 + 一条判据 + 一种反馈格式**：

### 7.1 缩到实际尺寸再判断（含扁条取景实测）

把交付图裁成**实际界面尺寸**（含目标宽高比），出「上 / 中 / 下」三条带做对照，而不是看原图：

```python
from PIL import Image
im = Image.open(src).convert("RGB"); W, H = im.size
band = round(W * H_target / W_target)               # 目标比例对应的高度
for name, off in [("top", 0), ("mid", (H-band)//2), ("bot", H-band)]:
    im.crop((0, off, W, off+band)).resize((W_target, H_target), Image.LANCZOS).save(f"{name}.png")
```

**这条检查的价值有两层：**

- **取带差异巨大**。实测把一张 16:9 全景按 **3.4:1** 裁成三条带：**中带**（水 + 绿 + 建筑三者齐备）一眼就是"繁盛绿洲"；**上带**（大片天空 + 远景山）像"奇幻大陆全景"；**下带**（近景帐篷，顶部被裁断）像"市集的一角"。
  ⇒ 结论不是"能裁 / 不能裁"，而是「**能裁，但必须为该比例单独构图**」（焦点数量、元素体量、留白都要重定，不能直接拿大图裁）。
- **细节是否幸存**。缩到实际尺寸后若灯笼、纹样、小字等细节全部消失，说明**密度不匹配** —— 这是资产不合格，不是"缩略图看不清而已"。

### 7.2 风格审计要局部放大，不能看整体

把**画面最复杂的区域**放大 2× 再判断：有没有统一描边、材质是平涂还是写实渲染、有没有写实光影。整体缩略图看不出这些。

**审计表（逐项打勾 / 打叉，作为交付物写进规范）**：

| 规范要求 | 常见实际（AI 概念图默认风格） | 判定 |
| --- | --- | --- |
| 统一描边、线宽 N px | **完全没有描边线条**，全靠明暗塑造体积 | ❌ |
| 平涂 + 轻渐变、无写实光影 | 主光 + 大气透视 + 辉光 + 投影 + 环境光遮蔽 | ❌ |
| 统一轴侧 / 平行投影 | 强透视、有明确消失点 | ❌ |
| 信息密度可控 | 极高（远山 + 多座建筑 + 成片元素 + 人物） | ❌ |
| 无文字 / 色板锁定 | ✓ | ✓ |

> AI 图的**默认审美就是"越满越写实越好"**，与"可执行、可复用"的界面规范天然对立。审计表的作用是把"感觉不对"翻译成**可判定的硬指标**，否则争论会停在审美偏好上。

### 7.3 判据：可读性优先于风格统一

**不同资产类别可以有不同风格强度**，判据是「最终显示尺寸」。不要为了"风格统一"把小尺寸资产也做成写实：

| 资产类别 | 最终显示尺寸 | 要求 |
| --- | --- | --- |
| **操作对象**（物品格 / 图标 / 按钮内元素） | 小（实测 ≈ **126 px**） | **必须**描边 + 平涂 —— 否则"一眼分清 N 个格子里分别是什么"这条**玩法底线**破功 |
| **氛围画面**（场景横幅 / 背景 / 过场） | 大（实测 ≈ **882 × 260** 起） | 可放松，允许天光与轻微大气感，但不要写实材质与强透视 |

> 写实光影 + 无描边放到 126 px 上只会糊成一团。**这是可读性问题，不是审美问题** —— 把"好看"凌驾于"能用"之上，是这类评审里最常犯、也最贵的一次错。
> 所以推荐的落点是**路径 A+**：物品侧严守规范，场景侧放松 —— 两者的可读性要求本就不同，不必也不该用同一套风格强度。

### 7.4 退稿要转成**编号修订清单**

评审不达标的成图时**不要给形容词反馈**（"再手绘一点""更卡通些"）。把差距落成编号修订项，每条可执行、可直接拿去重出：

```
① 加描边   —— 全画面统一 6 px 圆头圆角 <色值>，与操作对象同一套线宽
② 改平涂   —— 去掉写实光影与大气透视，平涂 + 轻渐变（≤ 2 档明度）
③ 降透视   —— 改弱透视 / 近似轴侧
④ 大幅降密 —— 视觉焦点 ≤ 4 个，删掉 <逐个点名具体元素>，留出大面积渐变天空与地面
⑤ 保留     —— <逐条列出成图做对的项>
⑥ 元素放大 —— 约 1.5×，确保缩到 <实际尺寸> 后仍可辨认
```

**必须同时把成图做对的项逐条列出并保留**（元素齐全度、视觉焦点选择、文化语言准确性、无文字、占比正确…）—— 只骂不改，下一版会把做对的一起丢掉。
另：成图若在某处**优于规范**（实测：AI 给的紫橙暮色天空比规范里定的深蓝夜幕好看，且提供了暖光来源），应当**改规范去采纳**，而不是为了维持原规范而放弃更好的方案。

> ⚠️ **但采纳之后必须做一次「背景明度重审」** —— 换色往往连带改掉**背景的明度结构**，而每个文字 / 元素都是"落在某一段底色上"的，底色一变，对比度结论全部失效。
> 实测连带链：背景「纯深色平铺」→「暮色四段渐变」后，
> ① 画面**底部由深变暖橙** ⇒ 原本用灰棕 `#A89685` 的版本号小字**直接糊掉**，必须改深色（`#241B38`）；
> ② 主视觉元素要**上移**才能落在对比充足的深色区；
> ③ 品牌字标必须移到**中间紫色段**，金色才够对比（落在暖橙段会糊）。
> **纪律：凡背景的明度结构发生变化（平色 ↔ 渐变、换色相、加天光），都要逐条重跑一遍「该元素落在哪一段底色上 → 对比度还够不够 → 要不要换文字色或挪位置」。只在规范里改一个色值，不会自动带上这三条结论。**

### 7.5 定案时分清「硬指标」与「软指标」，别为差一个数返工

规范里的约束是两类，验收态度不同：

| 类型 | 例 | 判定 |
| :--- | :--- | :--- |
| **硬指标**（破功即不可用） | 有没有描边、平涂还是写实、小尺寸是否糊、有无文字、色板是否锁定 | **一票否决**，必须修 |
| **软指标**（差一点但主次分明即可） | 视觉焦点数量（规范写 ≤4，实测 5 个）、元素体量偏差、留白比例 | **看整体主次是否分明**，通常**不必返工** |

实测：某张终态母版有 5 个视觉焦点（规范写 ≤4），但**主次分明、绝对焦点清楚**（主建筑最亮最大），判定**通过、不返工**。若为差一个焦点重出，会连带丢掉这一版做对的所有东西。

> 纪律：**验收结论要写明「为什么这一条不返工」**，否则下一轮评审会拿同一句话再卡一次。

### 7.6 禁止项必须配「允许项白名单」★

**只写禁止项，会误杀「字面违规、但实际是行业常规且好看」的处理。**

实测案例：规范里写了「禁写实光影 / 禁写实材质（金属反射、次表面散射）」。成图的水面上有**镜像倒影** —— 字面上属于反射，按字面执行该判违规；但它其实是**风格化处理**（简化 + 波纹），很好看，且是该题材的常规手法。

**做法**：每条禁止项后面跟一句**明确允许的例外**：

```
❌ 禁写实材质（金属高光反射、次表面散射）
⭕ 但允许：风格化镜像倒影（简化 + 波纹）、暖色天光、轻微大气感
```

**判据**：当某个效果「字面违反某条禁止项，但实际是行业常规且观感好」，就把它写进白名单 —— 否则下游会照字面删掉它，下一版变难看，而你会误以为执行不到位。同样适用于动效、特效、构图（如「禁强透视」放不放行「轻微大气透视」）。

## 八、叙事过场（剧情幕）的界面与写作纪律 ★

阶段完成 / 章节推进处的**短过场**（15–25 秒对话页）是一类独立界面，有它自己的界面规格与**写作纪律**。写台词前先过一遍本节，否则会做出「界面没问题但情感落点跑偏」的东西。

### 8.1 界面规格要点

| 项 | 规格 | 理由 |
| --- | --- | --- |
| 背景 | 进度母版取景 + **高斯模糊**（约 24 px） | 不抢对话框的阅读焦点，同时交代当前场景状态 |
| 立绘 | 高约 900 px，置于画面 **end 侧** | **不得遮住对话框** |
| 对话框 | 距底 = 安全区 + 48，宽满内容宽，`面板底色` 96% 不透明 | 保证长句可读 |
| 文字出现 | **逐字浮现**（约 40 字/秒）；**点按画面 → 先立即显示全句，再点推进下一句** | 这是对话页的标准手感，缺了会被认为「卡」 |
| 推进指示 | 左下/右下角的呼吸箭头 | 让玩家知道「点这里继续」 |
| **跳过** | 右上角 `Skip` **常驻**，点击**直接返回不弹二次确认**；系统返回手势与之等价 | 剧情可跳过是基本尊重；二次确认 = 拦人 |
| 章节标题 | 每幕开头居中显示 2 s 后淡出 | 给玩家「进入新一章」的仪式感 |
| 资源显示 | **纯叙事页不显示任何资源数值、不做任何消耗** | 叙事页插入数值会立刻把情绪打断 |

### 8.2 省资产：**立绘只做主角一张** ★

短过场里往往有多个说话人（主角 / 路人 / 商队首领…）。**不要为每人各做一张立绘**：

- **只做主角一张立绘；其他说话人只更换对话框上的名字，不换图。**
- 判据：过场只有 15–25 秒，**玩家读的是字**；为此多做 N 张 900 px 高、带表情版本的立绘不划算。
- 这条要在文档里**明写为决策**，否则美术会按「每个说话人一张」报价。

### 8.3 情感落点必须匹配产品的核心心理动机 ★（最容易写错的一条）

**产品的核心动机是「家园与归属」，终章就不能是凯旋。**

实测案例：三幕的终章原可写「绿洲重获新生，欢呼胜利」，但那样会让人物从**守护者**变成**征服者** —— 对女性向产品这是方向性错误。最终落在克制的一句上（「这从来不是什么奇迹，这只是有人不肯离开的结果」），并把这条理由**写进文档**。

> **纪律：写终章前先回到产品的情感动机（如「家园与归属」而非「征服与扩张」），逐句检查台词有没有把人物推向错误的一方。** 「胜利/征服/统治」类词汇在归属型产品里是危险信号。

### 8.4 三幕的结构一致性：每幕收在同一句式上

多幕叙事要有**可辨识的结构骨架**，让玩家感到「这是一个完整的弧」。实测做法：三幕各收在一句**把「地方」翻成「家」**的话上 ——

| 幕 | 收尾台词 | 递进 |
| --- | --- | --- |
| I | Every home starts with one person who decides to stay. | 一个人**决定留下** |
| II | It is a home. | 外人**承认这是家** |
| III | It is what happens when someone refuses to leave. | 回溯成因为「**不肯离开**」 |

> 骨架写进文档后再填词，比「一场一场想」更容易保持一致。

### 8.5 台词写作四约束（写进文档，供后续补写时复用）

1. **英文短句**：每句 ≤ 18 词（对话页一行放得下，且符合短剧式节奏）
2. **无宗教用语**
3. **不影射现实人物 / 事件**
4. **情感落点 = 产品的核心动机**（见 8.3），不是通用爽感

## 九、资源耗尽页必须明示「免费出路」 ★

**任何因资源不足而阻塞玩家的页面**（体力面板、钥匙不足、抽奖券不足…），**必须同时列出「付费」与「免费等待」两条出路，且免费那条要明说。**

实测做法：体力面板给三条 —— ① `Buy 100 Energy · 30 Gems` ② `Go to Lamp · 7 Keys` ③ **一行无按钮的小字 `+1 every 2 min`**。

| 为什么第三条不能省 | 说明 |
| --- | --- |
| **零广告 / 无 IAP 兜底的产品里，这是唯一的时间出口** | 没有「看广告续命」这类兜底时，若页面只展示付费选项，玩家会**误判为 paywall** —— 直接流失，而不是等待 |
| 它把「卡住」重新定义成「等一会儿」 | 阻塞感与计费感的差别，全在这一行字上 |
| 成本几乎为零 | 一行 Caption，没有任何功能实现 |

> **判据**：页面上每一个「用钱解决」的按钮旁边，都要能找到一个**不花钱的对照项**（等待 / 做任务 / 开免费宝箱）。找不到，就补一个。
> 同理，**阻塞反馈本身**也要给出路而不是只报错：资源不足时点按钮应**引导到产出的地方**（跳转到产出模块并高亮 + 传 `intent=` 参数），而不是只置灰。

## 十、不可用项与异步流程的界面纪律 ★

### 10.1 异步支付（IAP / 内购回执）：**永远表现为「正在发放」，绝不报错**

**先澄清一个常见误区**：**支付面板由 App Store / Google Play 系统提供，不由我们设计。** 我们只做它**前后的两个覆层**（发起中 / 发放中）以及整个流程的容错 —— 不要花时间"设计支付页"。

| 场景 | 处理 |
| --- | --- |
| 玩家在系统面板取消 | 覆层淡出 → 回来源页，按钮回就绪态。**不提示、不报错** |
| 支付成功、回调正常 | 「发放中」≤ 2 s → 覆层淡出 + 目标资源数字滚动增长 |
| **支付成功、回调延迟** | **「发放中」一直保持**（脉动不停、不报错）；**允许玩家点遮罩关闭**，资源以「发放中」半透明态显示，下次启动自动补发 |
| 超过 N 秒无回执 | 不弹超时提示，只给一行 Footnote（如 `This can take a moment.`）后允许关闭 |
| 处理期间 | **所有购买按钮一并置灰**（防重复下单） |

> **为什么这是硬纪律**：**IAP 回调延迟是常态，不是异常。** 用弹窗报错会让玩家以为钱丢了 —— 而**客诉成本对单人/小团队是致命的**。规则只有一条：**永远表现为"正在发放"，把重试交给后台。**

### 10.2 本版不提供的功能：**隐藏，而不是置灰**

| 做法 | 后果 |
| --- | --- |
| ⭕ **隐藏**（如本版只有英语 → 不显示语言切换项） | 玩家无感，界面干净 |
| ❌ 置灰显示 | 玩家会以为「**有这个功能但用不了**」—— 反而制造疑问与客诉，比没有更糟 |

**判据**：这项功能**本版整个不存在**（不是"暂时锁着"）→ 隐藏；**存在但当前不满足条件**（等级不够 / 资源不足 / 未解锁）→ 才置灰并给解锁条件。
实测：本版只做英语时，设置页的语言项直接不显示，并在文档里写明「Phase 2 接阿语时再加这一行」。

### 10.2b 「预告态」是第三种状态，别拿禁用态凑合 ★

上一条说的是**默认**做法。但用户可能**明确要求**：「本版没有的功能也要看得见，点了提示待开放」（典型动机：给 live-ops 预留入口位、让首屏不显空、把未来的功能当作路线图露给玩家）。这时**不要**用禁用态画它 —— 两个状态的含义根本不同：

| 状态 | 含义 | 视觉 |
| --- | --- | --- |
| **禁用态** | **你不能用**（条件不满足：资源不足 / 等级不够 / 未解锁） | `opacity .35` + 灰 `--dim` |
| **预告态** | **功能还没做**（本版不存在，但位子先站着） | 降饱和 **`.60`**（不是 .35）+ **保留 1 px 细描边** + 角标 `Soon`；点按 → 短气泡 `Coming soon` |

- **必须写进规范的状态语言表**（「想表达 X 用什么」那张），并与禁用态**并列成两行**，否则实现时会习惯性复用禁用态。
- **要在「允许出现的文字」里补一句授权**（`Soon` / `Coming soon`）—— 否则零文本 / 极简文案纪律会把它判成违规。
- **新内容要同步清点**：多一个 `Coming soon`，就要去改「短气泡内容穷举」的**两处**（全局约定 + 异常收口节），以及审计脚本的对应检查项 —— 不查就立刻变成「同一清单两处不一致」（正是 §5.1 那条老毛病）。
- **数量克制**：一行死入口对首屏是负分。**一期放 2–3 个足够，留空位比填满干净。** 这条要写进文档当作给未来的约束。

### 10.3 玩家主动关闭 = 完成，不是取消

对**纯增益**的弹窗（回归礼包、结算奖励），**遮罩点击与系统返回应当等价于主按钮**，**不留「取消」**。

- 理由：这是礼物，不该被拒绝；留「取消」只会让玩家少拿东西，对留存是纯负面
- 同理，**赠送类弹窗不应有二次确认**

## Writing Process
1. **先立 00 总览** — 系统清单 + 系统关系图 + 统一约定（术语、跨系统规则），再逐系统展开
2. **每个系统「策划案 + 交互案」成对产出** — 先策划案定规则，交互案从策划案的 Harness/规则里推导状态机与操作矩阵
3. **通用交互案最后写** — 把所有分系统交互案里的「跳转 XX」汇总成跳转映射表，逐条补落地/返回/传参
4. **美术规范收口** — 等所有页面梳理完再定色板/字体，避免反复改

## Pitfalls
- **只写策划案不写交互案** → 前端无法对齐交互细节
- **跨系统跳转只写「跳转 XX」缺落地/返回/传参** → 系统沦为孤岛，靠「通用交互案」补
- **分辨率横竖屏写反** — 常见笔误：把竖屏写成「1920×1080(16:9)」。竖屏应为 **1080×1920(9:16)**，横屏才 1920×1080。写美术规范前先与用户确认画布方向（小程序默认竖屏）
- **美术规范只给形容词不给 HEX/px** → 无法指导 UI 生成，必须落到可执行参数
- **空态是空白死路** → 所有空态必须带引导动作
- **patch 中文文档误用半角引号** — 用 patch 的 `new_string` 修改中文 markdown 时，手误写半角 `"` 会替换掉原文的中文引号 `""`，造成全篇引号混用。改完用脚本断言 `raw.count('"') == 0`（或统一替换回中文引号）再交付；中文正文里的引号应始终是 `""`，不是 `"`。

- **入口页与详情页做成平级** — 判断层级：Tab 直达 = 主页面，从入口点进 = 下级页；「我的」是入口聚合页，成长中心/看板是它的下级，**不要平级**
- **把「主场景」与「关卡」压成一层**（关卡型 / 二合产品最致命的一处架构乱）→ 入口、进度、局内数据、快捷方式全堆在一个页，出口数与返回路径爆炸、组件规格与用法对不上、布局算不平。有「局外经营 + 局内作业」双形态的产品，**先拍「两层各挂什么 + 落地页是哪层」再画界面**（见 §6.1）
- **把「经营目标」只做成清单 / 按项目条目数去画坑位** → 目标要**看得见**：把待建位预画进场景底图当**坑位**（残破底座），**坑位数 = 族位置数，不是项目条目数**（实测 23 个项目 → 5 个族位）。用「禁用态」画坑位 = 把目标画成坏了，玩家会当 bug。另：**改画布方向（横→竖）时方图物件资产可复用**，只有母版与「出现/不出现」两态总图要重出，旧母版转商店/买量素材 —— **先做这张分类表再报价**，否则会按「全案重出」估出约 3 倍成本。见 `references/scene-as-management-goals.md`
- **做界面时不定入口/出口、事后补导航** — 结果是界面成孤岛；做每个界面时同步写清上游（从哪进）与下游（按钮去哪）
- **为「能力/体系/看板」单独建文档** — 它该融入所属模块，别造独立的《XX体系》文档
- **美术规范缺文字体系** — 只给色彩/间距「过于简单」，必须含 8 级字号 + 颜色体系 + 排版规则
- **没确认语言范围就写排版/布局章节** — 多语与 RTL 会改写整整一节：镜像判定表、字号补偿（阿拉伯语 ×1.08）、行高补偿（×1.15）、文案长度预算（×1.5）、字体打包要求。本会话先按「阿语 RTL 优先」写了完整一节，用户随后拍板「这个版本只考虑英文版本，不考虑阿拉伯文的镜像设计」→ 整节重写。**写规范的第一件事是问清：本版支持几种语言、有没有 RTL / 竖排 / 超长语言。** 同理，多语产品要先问清「目标市场与语言是否一致」（英文界面投中东 ≠ 泛英语市场，两者的成功标准与买量素材完全不同）。
- **被暂缓或未启用的方案移入附录存档，不要删** — 用户关掉某项设计（如不做 RTL）时，把完整推演压进 `附录 X：…（暂缓，本版不实施）`，写明「状态 / 启用条件 / 保留原因」，正文对应位置留一行指向附录。删掉将来要重做，存档几乎零成本。
- **正文一律用 start / end 描述布局，即使本版不做 RTL** — 这条零成本，且把将来接 RTL 的成本预付掉（只需加一层镜像，不用重画任何布局）。写 `left: 60px` 会变成隐藏债务。
- **合规红线不要跟着语言一起删** — 文化/宗教/形象类红线**不绑定界面语言**：英文界面投中东市场，照样会被同一套审核下架。语言范围收缩时，把「与语言无关的合规节」单独拆出来保留并注明「本版仍适用」。
- **不写布局算式就直接画界面** — 各段高度相加与画布对不上、组件宽度与容器算不过来，往往画到一半才发现要重排。写界面提示词的第一步就是把纵向/横向算式列出来，它会替你撞出规格冲突；撞出来的修正要回补规范并升版本，且把「上限/下限」型结论写成显式约束。见 §四.5
- **全量界面做完不做审计** — 跑 `scripts/audit_interaction_docs.py`（六项）或 `scripts/audit_screens.py`，孤儿/死链/命名不一致/未定义取值必须清零再交付
- **把「冗余」当「错误」来 FAIL** — 审计里分清严重级：**「用了但没定义」是硬错误（一票否决），「定义了但没用」只是冗余（只作提示）**。第一版脚本把后者也算失败，等于让工具替人决定删掉调色板里的纯白。**凡把非错误当失败，工具就会被绕过、最终被弃用。** 见 §5.1
- **把审计脚本当成「设计正确性」的保证** — 脚本只查机械一致性（有无定义 / 有无入口 / 有无死链），**查不出数值是否对齐、交互是否合理、提示词能否出图**；也不区分「设计使用」与「行文提及」，且查不出「没进清单的界面」。局限要在文档里写明，否则下一轮会拿它当万灵药、或反过来因一次误报而整个弃用。见 §5.2。**用户说一份交互案「混乱」时，先跑 `references/ia-and-consistency-chaos-patterns.md` 的四类排查，再动手改** —— 那不是脚本能报出来的东西。
- **审计计数对不上就怀疑「编号被加粗了」** — 脚本正则要求 `| S21 |` / `| J53 |` 这种**编号紧跟竖线**的形态；写成 `| **S21** |` 该行会被**静默跳过**，症状是「清单声明数与实际交付数对不上、新界面被报成孤儿与死链、但两个方向都显示 ✓ 无差异」。**它不报错，只是少算**，最容易被误判成方案有问题。见 §5.3 第 3 条。
- **待决策项不定义术语** — 用户会反问「XX 是什么」，等于白问一轮；每条待决策都要能独立读懂（见 §六.5）
- **合规要求只写在规范里、没落到界面** — 下游（美术/前端/外包）看不见；注册商标规避、地区禁项视觉、概率公示页都要写进**对应界面**的提示词与禁止清单（见 §六.5）
- **生成的界面提示词不留「术语占位」** — 提示词里的文案要按真实语言的实际长度写（英文就写英文串），不留 `Lorem ipsum` / `TODO`，否则出图会自带一批占位文字
- **凭原图观感验收 AI 出图** — 概念图级密度缩到实际界面尺寸后细节全糊，且会与相邻清晰元素抢注意力。必须在**最终显示尺寸**下判断：缩到实际尺寸 + 出「上/中/下」三条带对照 + 2× 局部放大做风格审计。见 §七
- **为了"风格统一"把小尺寸操作对象也做成写实** — 实测 126 px 的物品格上，写实光影 + 无描边会糊成一团、分不清边界，**玩法可读性底线破功**。判据是「最终显示尺寸」：小尺寸操作对象必须描边 + 平涂，大尺寸氛围画面才可放松。这是可读性问题不是审美问题，见 §七.3
- **退稿只给形容词反馈**（"再手绘一点""更卡通些"）→ 美术无法执行，下一版还会漂。要落成**编号修订清单**（每条可执行），并**同时逐条列出成图做对的项**，否则重出时会把对的一起丢掉。见 §七.4
- **成图某处优于规范时仍死守规范** → 该改规范去采纳（实测：AI 给的暮色天空比规范里的夜幕好看且提供了暖光来源，采纳后规范更强）。规范是服务于结果的，不是反过来
- **换了背景明度结构却不重审文字对比度** → 背景从平色改渐变（或反之）、换色相、加天光，都会改掉**每个元素所处的底色**。实测采纳渐变天空后底部变暖橙，灰棕小字直接糊掉，且主视觉要上移、字标要挪到中间深色段才保住对比。**改一个色值不会自动带上这些结论** —— 要逐条重跑「该元素落在哪段底色上 / 对比度够不够 / 要不要换色或挪位」。同理，换代后要 grep 全案扫废弃取值的残留（见 §五 第 8 条）
- **命名方案迭代后不记录"已废弃"清单** → 同一套命名会被翻回来重议。在命名对照表下方加一行「**已废弃命名方案（勿再使用）**」，列出每一版被否掉的名称 + 否掉的原因（文化 / 合规 / 语义撞车）。
  实测：命名迭代了三版才定 —— ① 魔法化（魔力 / 净化符 / 法阵）② 中东文化化（水 / 珍珠 / 织毯）③ **中性名 + 少量文化点缀**（体力 / 宝石 / 棋盘 + 香料坊 / 一千零一夜）。不记录黑名单，下次会重新提议第一版。
- **默认给核心术语做文化/世界观包装** → 往往被高估。**核心资源名保持中性更实用**：文化包装名容易与场景里的实体语义撞车（实测：把「体力」包装成「水」，会与场景里的引水渠 / 蓄水池 / 水晶湖全部撞车），且玩家每天看几十次，中性名反而更好读。包装留给**能承载氛围的名词**（场景道具、宝箱、叙事物件），别动玩家高频读的资源名。
- **命名不接受不存在的检查项** → 对外名称定名前必过三关：① 既有品牌 / 游戏 IP 冲突（搜一遍）② **宗教专有名词**（国内直觉最易漏，实测 `Rawda/Rawdah` 在伊斯兰语境指麦地那圣寺圣区，用作产品名直接违规）③ 酒 / 烟草 / 赌博联想（实测 `Nakhla` 是埃及水烟烟草品牌）。造词天然避开冲突但**不等于商标安全**，最终法务检索归用户。详见 `mena-market-naming-and-compliance`

- **禁止项不配「允许项白名单」** → 字面执行会误杀「字面违规但实际是行业常规且好看」的处理（实测：水面的**风格化镜像倒影**被「禁写实材质」按字面判违规；它其实是简化 + 波纹的常规手法）。**每条禁止项后面要跟一句明确允许的例外**，否则下游照字面删掉，下一版变难看。见 §7.6
- **为差一个数返工（焦点数 / 体量偏差等）** → 规范里的数值约束分**硬指标**（描边 / 平涂 / 小尺寸是否糊，一票否决）与**软指标**（焦点数量、体量偏差、留白比例，看主次是否分明）。实测 5 个焦点（规范写 ≤4）因主次分明**判定不返工** —— 为差一个数重出会连带丢掉做对的全部。**验收结论要写明「为什么这条不返工」**，否则下一轮会被同一句话再卡一次。见 §7.5

- **过场叙事给每个说话人各做一张立绘** → 短过场（15–25 秒）玩家读的是字，**只做主角一张**，其余说话人只换对话框名字、不换图。这条要**明写为决策**，否则美术会按「每个说话人一张」报价（§8.2）
- **终章写成「凯旋 / 胜利」** → 若产品的情感动机是「家园与归属」，凯旋会把人物从**守护者**变成**征服者**，情感落点方向性跑偏。终章要克制，并把这条理由写进文档；「胜利/征服/统治」类词汇在归属型产品里是危险信号（§8.3）
- **多幕叙事没有结构骨架** → 一场一场单独写必然散。先立一条贯穿各幕的**句式骨架**（实测：三幕各收在一句「把地方翻成家」的话上，形成「决定留下 → 承认是家 → 不肯离开」的递进）再填词（§8.4）
- **资源耗尽的页面只给付费出路** → 零广告 / 无 IAP 兜底的产品里，玩家会**误判为 paywall 直接流失**，而不是等待。每个「用钱解决」的按钮旁必须有一个**不花钱的对照项**（等待 / 做任务 / 开免费宝箱），且免费那条要明说（§九）
- **资源不足只置灰、不给出路** → 阻塞反馈要**引导到产出的地方**（跳转产出模块 + 高亮 + 传 `intent=` 参数），而不是只把按钮置灰（§九）
- **异步支付用弹窗报错** → **IAP 回调延迟是常态不是异常**，报错会让玩家以为钱丢了，客诉成本对小团队致命。规则是「**永远表现为正在发放、绝不报错**」，把重试交给后台；另注意**支付面板由系统提供，不要自己去设计支付页**（§10.1）
- **本版不提供的功能置灰显示** → 玩家会以为「有这功能但用不了」，反而制造疑问。**整版不存在 → 隐藏**（如仅英语版本就不显示语言切换项）；**存在但暂不满足条件 → 才置灰**并给解锁条件（§10.2）
- **纯增益弹窗留「取消」** → 回归礼包 / 结算奖励这类"礼物"不该可被拒绝，**遮罩与系统返回应等价于主按钮**，不留取消、不做二次确认（§10.3）
