# 策划案设计工作流

## When to Use

撰写产品/游戏系统策划案时，尤其是：
- 需要把一个大产品方案拆分成多个子系统
- 需要为每个系统写策划案（设计目的/规则/数值）
- 需要审查已有策划案（拆分是否过度、数值是否缺失、是否混入验收）

## 核心工作流（5 步）

```
① 拆分系统 → ② 写策划案 → ③ 补数值 → ④ 剥离验收 → ⑤ 迭代审视
```

| 步 | 产出 | 要点 |
| :--- | :--- | :--- |
| ① 拆分系统 | 系统框架 | 按「业务价值 + 规则复杂度」分层 |
| ② 写策划案 | 每系统策划案 | 设计目的/系统规则/系统关系 |
| ③ 补数值 | 数值层 | 具体数字/公式/阈值，**不留「待定」** |
| ④ 剥离验收 | 独立验收文档 | 验收是测试阶段的事，不进策划案 |
| ⑤ 迭代审视 | 矛盾/循环检视 | 多文档冲突 + 逻辑自洽 |

## 原则 1：系统拆分标准

一个东西配不配叫「系统」，看三点：
1. 有没有**独立业务价值**（不依附别的系统）
2. 有没有**足够的规则复杂度**（值得单独策划）
3. 有没有**独立的产品逻辑**

不满足的 → 是「能力/组件」，该归入所属系统，或合并为「平台能力层」。

**分层**：
- **业务系统**：有独立业务价值、规则复杂
- **平台能力**：横向支撑的技术能力（账号/消息/支付/埋点…）

## 原则 2：避免拆分过度

**常见坑**：把「能力/组件」当「系统」，导致系统数量膨胀、个案内容单薄。

**判断信号**：某个系统策划案只有几行 → 它是能力，不是系统。

**修正**：
- 合并同类能力（账号+权限+用户中心 → 账号与身份）
- 把「能力」并入所属业务系统（搜索→推荐、审核/风控→治理）
- 用「平台能力层」收录横向技术能力

## 原则 3：策划案结构

```
# <系统名> · 策划案
> 一句话定位
## 一、设计目的（背景痛点 + 目标）
## 二、系统规则（核心机制/状态机/Harness）
## 三、数值（具体数字/公式/阈值 + 数值汇总表）
## 四、与其他系统的关系
```
- 每系统配「交互案」（页面流/操作矩阵）→ 见 [[interaction-design-workflow]]。

## 原则 4：数值层必须具体

- **不留「待定」**：等级阈值、XP 数值、权重公式、汇率——都要给具体值。
- 给**数值汇总表**（研发配置用）。
- 数值是初始值，落地前需业务数据校准。

## 原则 5：验收剥离

- 验收指标（量化目标）属于**测试/验收阶段**，**不进策划案**。
- 全部剥离到独立的「验收指标汇总」文档。

## 原则 6：迭代审视

- **矛盾分析**：多份文档之间是否有冲突/不一致？
- **循环检视**：核心循环 + 子循环是否逻辑自洽？与理论框架（如八角）有无冲突？

## Checklist

- [ ] 系统拆分按「业务价值 + 规则复杂度」
- [ ] 无拆分过度（无内容单薄的「系统」）
- [ ] 业务系统 vs 平台能力已分层
- [ ] 每系统策划案结构完整（目的/规则/数值/关系）
- [ ] 数值具体（无「待定」）+ 数值汇总表
- [ ] 验收指标已剥离到独立文档
- [ ] 做过矛盾分析 + 循环检视
- [ ] 每系统配交互案
